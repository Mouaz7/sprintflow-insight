# 0020: Flow history, advisory WIP and statistical review

Status: Accepted for B5. Date: 2026-11-17.

The new flow module is pure Java. Reporting loads project tasks, ordered history and WIP settings in a fixed number of queries, then assembles records for a lazy `/flow` page. V21 adds the project/time history index and project-scoped WIP tables; V17–V20 remain unchanged. A binary search resolves daily snapshots, including deterministic insertion-order ties. Same-status snapshots are collapsed. Future imported events are excluded at evaluation time.

The analysis uses whole UTC days ending now and current visible project scope. Later trash/permanent deletion can therefore change older counts. This differs deliberately from a completed sprint's immutable delivery snapshot. Missing history is excluded from historical times/charts, with coverage shown; current column counts still include every live task and match the board. Percentiles are Hyndman–Fan type 7 over window completions, in elapsed hours. Only the latest completion of a currently completed task is counted; null or invalid durations are omitted. Lead time starts at creation. Cycle time starts at the uninterrupted In Progress/Review run that ended in Done. To Do or reopening starts a new run; movement between active columns does not. The existing metrics summary now shares this definition, correcting resets when Review returns to In Progress. Summary rounding remains one decimal, analysis two.

WIP limits are advisory and use all column tasks, independent of board filters. Owner/Admin can replace them in an active project; all members can read archived projects. The parent project row lock serializes replacements. If-Match refers to a collection revision retained even when every limit is cleared; missing configuration starts at revision 0. A stale administrator cannot silently overwrite another change or reuse a cleared revision. Activity events refresh connected project views. Over-limit active columns are highlighted first, otherwise the highest time-averaged active WIP; the UI calls this a possible bottleneck rather than proof of a capacity constraint.

XmR uses the sample mean, successive absolute moving ranges, sigma=MRmean/1.128, individual limits mean±3sigma and MR upper limit 3.267 MRmean. It applies the four Western Electric rules (outside 3 sigma, two-of-three beyond 2 sigma on one side, four-of-five beyond 1 sigma on one side, eight on one side) and a large-moving-range rule. Individual lower limits are clipped to zero only for display. Six measured cycles permit a descriptive chart; this is not a validated baseline. Multiple rules, autocorrelation and skew can increase false alarms. Signals invite inspection, not automatic process changes. Constant decimal series are handled without summation-induced false signals. Limits use the full retrospective window; graphs show at most 200 recent points while signals and metrics use the whole window.

Little's law compares time-integrated active WIP with measured-cycle throughput × mean active-cycle duration. The ratio band 0.80–1.25 and minimum five measured completions are explicit product heuristics, not statistical significance thresholds. Censoring at finite-window boundaries, reopened work and changing demand can explain disagreement without corrupt data. The UI asks the team to review the boundary/history instead of asserting a data-quality failure. Finished-only percentiles have survivorship bias; ongoing task ages are shown alongside them.

Sources: [NIST individuals charts](https://www.itl.nist.gov/div898/handbook/pmc/section3/pmc322.htm), [NIST control-chart rules and false alarms](https://www.itl.nist.gov/div898/handbook/pmc/section3/pmc32.htm), [NIST percentile conventions](https://itl.nist.gov/div898/handbook/prc/section2/prc262.htm), and [Little's original proof](https://pubsonline.informs.org/doi/10.1287/opre.9.3.383). These support the methods; the finite-window review tolerance and display limits are our design choices.

No runtime chart dependency is added: SVG, keyboard controls and HTML table alternatives reuse A7. The all-route JavaScript budget grows explicitly 240→255kB gzip (measured 251.54kB), with a separate 20kB flow route limit. Entry 125kB, CSS 15kB and existing route limits remain unchanged. WIP drafts keep their captured version and values during refetch or rejected saves; one dialog survives loading so focus is preserved.

Verification includes independent hourly-ledger and affine-signal properties with fixed seeds, NIST reference values, PostgreSQL role/revision/concurrency/upgrade checks, exact OpenAPI records, MSW UI tests, packaged browser/axe flows and a two-year-history k6 profile. Results are recorded in the B5 completion evidence.
